# fixstall3: DRILLS7 findings F10 to F12

> status: offline fixes; none verified live yet (live recipe below). Follows [fixstall2.md](fixstall2.md).

## Root causes and changes

- F10 (H.pause, 3 of 6 tries stall at 25.9,20.5). `planAround` (internal/d2dctl/approach_path.go) required clearance 1 around every route cell. The stall cells sit in a gap 1 to 2 subtiles wide against the east face of a camp block, so no clearance-1 route exists and `routeAround` returned false twice. Fix: `planAround` tries clearance 1 first and falls back to clearance 0 (`planAroundClear`); NPC blocking, standoff 6 and the no-corner-cutting rule for diagonals are unchanged, so a clearance-0 route never cuts a block corner diagonally (both side cells must be free). Test `TestPlanAroundRealCampStallCells` loads the REAL `debug grid 5` crop (internal/d2dctl/testdata/camp-grid.txt, copied from DRILLS7): routes exist from all three stall cells and the arrival cell, end on a free cell within the standoff of Kashya, and the arrival cell keeps its clearance-1 route. UNVERIFIED: that the game's walker follows a clearance-0 route along the 1 subtile gap (the legs are `cmd move` to cells every 12 subtiles; if a leg stalls, `routeAround` returns false and the blind side step runs as before).
- F11 (D6.d). `town.enterPortal` skips `GoTo` only for an input that implements `town.WalkingInteractor`; that is `d2dtown.townInput` (built by `d2dtown.Input`), but the bot (cmd/d2bot/d2dwire.go) and the drill harness (cmd/d2drill/live.go) built the town on `HoverFirstBelt`, whose Interact is the controller one-shot (and whose portal path is the uncalibrated `UsePortal`). Fix: both use `d2dtown.Input(be.Ctl, be.Client)`, which also provides BeltPut and MoveGold, and whose Interact is `EnterPortal` / `ApproachNPC`. Tests: `TestInputIsWalkingInteractor` (compile-time assertion plus runtime check for portal and NPC ids and BeltPut) and the existing `TestEnterPortalDoesNotWalkWhenInteractWalks` (town package, fake backend: no GoTo). Side effect: the bot's NPC interactions now take the ApproachNPC route too (that was the fixstall intent, never wired in the bot).
- F12 (D-sync.wp run 2: 0 of 3 killed, 12 approaches each, no unreachable line). Cause NOT isolated, UNVERIFIED. What the logs give: both runs start identically (nav plan 8 cells east, two clicks), the town-portal arrival passes 3 of 3, so the Fighter code is the same and the difference is the run (zombie spawn positions near the waypoint, which vary; the ignore fires from `engage` when `inReach`, `onScreen` or `los` stays false while the approach walk does not close the 7 to 8 subtiles). Candidates: the spawn ring has an obstacle between (assess says walkable, the walk stalls), a stale snapshot position after the waypoint trip, or LOS blocked. No product defect could be shown offline, so no behavioural change; the `ignoring target why=approaches` reason now carries player and target cells and the inReach, onScreen and los flags. Next probe: rerun D-sync.wp x3 on the worker host and read those fields from the log; if player and target cells do not move between approaches the walk is stuck (capture `debug grid 5` around the player), if cells move and los=false the monsters stand behind walls.
