# Ethereal Vault store (internal/vault) and its file formats

> status: V2 store BUILT offline, V3 bot wiring BUILT offline (section 'Bot wiring (V3)'), V4 read API and page BUILT offline (section 'UI and API (slice V4)'), V5 Keep queue BUILT offline (section 'Keep (slice V5)', live drill NOT run) (slice V2 of docs/design/loot-vault-2026-11-16.md). Sell is instant since 2026-11-22: section "Sell is instant" below. Additive and unused until V3 (rules action) and V5 (keep queue) call it. Not run against a live game: every claim below is about the offline package (V: `go test ./internal/vault/`). Item hex comes from the fork codec later (V1); here it is opaque bytes.

## Layout (per hero)

`<root>/<hero>/vault/` (`vault.HeroDir`), hero key validated (no `/ \ :`, no `..`, 64 chars max).

| File | What | Durability |
|---|---|---|
| `log.jsonl` | the truth: one event per line, append-only, `O_APPEND`, fsync per event | a torn last line (no newline) is cut on open; a complete bad line is skipped and counted (`Status.Anomalies`) |
| `index.json` | snapshot of the replayed state plus `offset` and the sha256 of the last covered line | a CACHE: missing, damaged, other hero or not matching the log = full replay; temp file + rename |
| `archive.jsonl` | every record that left the vault (trim, discard) with time and reason | written and synced BEFORE the log line that removes the record |

Capacity and the account wallet are not stored here: the vault reads capacity through `Options.Capacity` (a func read at every insert) and the `Account` / `Wallet` interfaces in `capacity.go` (V7 implements them over the ledger).

## Log events

`{"seq":n,"ev":"...","id":"v-...","t":"RFC3339","item":{...},"trim":"v-...","reason":"...","n":0}`

| ev | from state | to | note |
|---|---|---|---|
| `add` | (new) | recorded | carries the whole item; `trim` names the displaced record (one line, so insert-with-trim is atomic) |
| `pin` / `unpin` | recorded | recorded | flag only; pins capped at `pinPercent` of capacity |
| `keepq` | recorded | keepq | Keep clicked |
| `kbegin` | keepq | keepq, `inflight` | logged BEFORE the game create is sent; a second `kbegin` is refused |
| `kept` | keepq | kept (final) | create confirmed |
| `kretry` | keepq | keepq, not in flight | the create is known not to have happened |
| `keepfail` | keepq | recorded | reason on the card (nospace, version, dead) |
| `keepcancel` | keepq (not in flight) | recorded | |
| `reveal` | recorded | recorded, identified | carries the identified item bytes; the id stays, the content hash changes |
| `sellq`, `sellfail`, `sold` | recorded / sellq | sellq, recorded, sold (final) | V6 |
| `discard` | recorded | discarded (final) | archive line first |

States: recorded, keepq, kept, sellq, sold, discarded, trimmed. "Pinned" and "revealed" from the design are flags shown by `Rec.Status()`, not states (a pinned item can also be revealed). Live states (recorded, keepq, sellq) count against capacity; final ones do not.

## Identity and dedupe

d2d items have `uid` 0 (V0 finding), so identity is `sha256(raw bytes)[:8]`. ID is `v-<hash16>`; the same bytes recorded again after the first record finished get `v-<hash16>~<generation>`. While a record with the same bytes is live, Add returns `ErrDuplicate`. Two genuinely different drops with identical bytes (two Minor Healing Potions) therefore collapse into one live record: the vault stores distinct items; stackables are a V3 decision (record as one item with a count or skip). U: whether real different drops can ever share bytes outside stackables.

## Capacity, trim, shrink (data/vault/capacity.json, value.json; numbers are placeholders)

- Capacity = `base` plus owned steps, capped at `max`; `Tiers.Capacity(owned, override)`; unknown step ids are ignored.
- (Default since 2026-11-21: NO trim, see "Decision 2026-11-21" below. The next line is the behaviour with `loot.vaultAutoTrim` 1.) Insert at exact full (count == capacity) trims ONE record first: lowest `value`, then lowest ilvl, then oldest, among unpinned `recorded` records. Protected items (qualities set, rare, unique, crafted; runes, jewels, charms by code prefix, from value.json) go only when nothing else is left AND `Options.TrimProtected` is set, otherwise `ErrFull`. The victim is archived first.
- Over capacity (count > capacity, after a shrink): Add returns `ErrOverCapacity`, nothing is trimmed, nothing is deleted; recording resumes once discards or keeps bring the count back to capacity.
- Value (`ValueTable.Of`) is computed at Add and stored, so replay never changes a trim order. It does not reuse the loot rules (those decide pickup; none of their helpers rank records).

## Keep crash recovery

Order: `Keep` (keepq) -> `BeginKeep` -> game create -> `CompleteKeep`. After a restart `Recover(present)` looks at records in flight and asks `present(rec)` (is that item in the stash): yes completes the keep, no clears the mark so it is queued again, an error leaves it in flight. The create is therefore sent at most once per confirmed state; the one unavoidable window (create done, `kept` not logged) is closed by the stash check, never by sending again.

## Export / import (`Store.Export`, `Store.Import`)

`{"version":1,"hero":"...","items":[Item...]}`: live records, oldest first. Import: at most 64 MiB and 5000 items, version must match, every item validated before any is added; items go through Add (dedupe, capacity; import never trims, it counts `Blocked`). Not the wallet: a hand-edited wallet is a cheat (design 2.6).

## Measured (V, `go test -bench`, a small 4-core box, NoSync, indicative only)

Insert about 8 us (10k and 50k); insert with trim at 10k about 0.6 ms; Open by full replay 59 ms at 10k and 296 ms at 50k; Open with snapshot about 270 ms at 50k (JSON decode dominates, so the snapshot does not beat replay yet: U whether a binary snapshot is worth it); query with code+quality+ilvl+sockets about 0.6 ms at 10k and a name substring scan about 10 ms at 50k. fsync cost per event is not in these numbers.

## Bot wiring (V3, `internal/loot/vault.go`, `cmd/d2bot/vaultwire.go`)

Offline only (U live). With `loot.vault` 1 the ground stage uses the Vault preset (docs/lootrules.md section 14); for a `vault` decision `Looter.vaultOne` walks like a pickup, calls `GroundFull` for the unit, builds a `vault.Item` from the fork's `norm` bytes (the create key) plus code, quality, ilvl, sockets, identified and ethereal as the fork reports them (an unidentified item keeps its roll and bit), and calls `Store.Add`. Outcomes: recorded; `ErrDuplicate` (counted, never revisited); full (blocked 2 min, one Needs-you line per episode, items skipped as `vault full`); anything else (peek refused, unit gone, store error) marks that unit as fallen back and today's pickup decision applies. `ErrVaultUnsupported` / `ErrVaultOff` also make the feature inert for the process. Records of one game are told apart by unit id plus spot, so a recorded drop is not walked to twice; the vault dedupes by content, so two identical stackable-like drops collapse into one record (see Identity above).
`Looter.VaultInfo()` (active, inert reason, blocked, recorded, dups, fallback) is the visible state. `wireVault` opens `<data>/vaults/<hero>/vault` on the first record. Measured runs: `D2BOT_RUN` forces the knob to 0 (the same detection as gear policy and the item-verb fast lane).
Not done: `ground take` after recording (Keep slice V5 creates from the record), the Needs-you row itself (V3 emits a log line through `VaultWiring.Notice`), the `/api/vault` page (V4), a Vault entry in the preset list of the store.

Log compaction (design 5: archive-then-replace at 3x live data); the trashed-list purge schedule (`PurgeArchive(before)` exists, nobody calls it); wallet (V7); the item codec that fills `Raw`, `Name`, `Chain` (V1).

## Keep (slice V5: `internal/vaultkeep`, `POST /api/vault/keep`)

> status: BUILT offline, not run against a live game. V: `go test ./internal/vaultkeep/ ./internal/vault/ ./internal/watch/ ./internal/bot/ ./cmd/d2bot/` (queue, executor and recovery against `d2dctl.VaultFake` on a Sorceress and a Paladin hero), the fit pages `vault-keep*` and the pictures `tools/uishots.sh --vt --only 'keep*'`. U: everything that needs the fork (the `item create` byte round trip with real items, `item full` listing stash items, the stash proximity of the verb, `save` after a create); the live drill below checks them.

Knobs (docs/knobs.md): `loot.vault` 1 (the vault itself) and `loot.vaultKeep` (default 1) both on, otherwise the Keep gate answers `off`; `loot.vaultKeepPerVisit` (default 20). Forced off in measured runs (`D2BOT_RUN`, as gear policy and the recorder). `loot.vaultKeep` 0 is the kill switch: nothing is created at once, queued items stay queued.

Flow. The player presses Keep (card, or "Keep (n)" in the selection bar): `POST /api/vault/keep {ids, target?, now?}`. `target` is `stash` (default) or `inv`. The route only QUEUES (`Store.KeepTo`: recorded to keepq); it never creates anything and there is no instant lane. The reply is `{ok, done[], already[], failed[{id, code, error}]}`; the page shows the real sentence and then reads the state back from `GET /api/vault` (`keep` object: enabled, why, queued, creating, done, full, line; each row: `keep` = queued, creating, kept or failed, `reason`, `where`). Refusals before anything is queued (409): `off` (knob off or measured run), `dead` (hero dead), `verbs` (the d2d build lacks `item.create`), `stopped` (a read-back mismatch tripped the switch for this run); per id: `missing`, `state`, `target`.

Idempotent: a record that is queued or kept answers ok with `already`; the state machine refuses a second `kbegin`; the create carries `key=vk-<record id>`, so the fork refuses a second create in one game too (`dup`).

Executor (`Keeper.Run`, called by `bot.vaultKeepStep` after the player's own item actions): only in town, alive, no blocking panel, cursor free (`keepReady`, from the last snapshot), no fight, no trip (the bot's `safeMoment`). Per call: at most `loot.vaultKeepPerVisit` creates and 8 s of wall time (`Keeper.Budget`); the bot retries a queue that did not move after 30 s, a changed queue length at once, so a long queue never stalls the chores. Order per item, each step a line of the vault log:

1. take the save backup before the FIRST create of the process (`Backup`: the fork's `save` verb, which writes through the character store, reads the bytes back and keeps its `.bak`; `saves.Snapshot` is not usable, it refuses in a game and the d2d path has no save directory). A failing backup stops the batch (fail closed).
2. `BeginKeep` (logged BEFORE the verb), `item create <raw hex> stash|inv key=vk-<id>`; the verb returns the unit id and the cell.
3. read-back: `item full <unit>` must equal the recorded bytes (`Raw` = the fork's norm bytes). A mismatch removes the new copy again (`item vault`), fails that record with the reason, and TRIPS the keeper: nothing more is created until the bot restarts, and a Needs-you row says so. The record itself never leaves the vault on a Keep.
4. after the batch, ONE `save` (read-back and `.bak` are the fork's); only then `kept` is logged for each item with where it landed (`stash 3,5`). A failed save leaves the items in flight; the next run looks at the hero, sees them, saves again and confirms: it never creates a second one.

Unidentified items are created unidentified (the bytes are the drop's); identify stays the normal step.

Crash and failure recovery (V: tests `TestRestart*`, `TestSaveFailure*`, `TestUnanswered*`): a record still in flight is resolved first by `item full` (is there more of this item in the hero than kept records of the same bytes the vault already counts?): present completes it, absent queues it again (`kretry`); a transport error or timeout on the create itself leaves it in flight for the same look. Never by creating again. U: a player who moved or sold an identical earlier kept copy makes the count too low and one more copy may be created; the key of the fork covers the same game.

Failure reasons (stored `keep: <sentence>`, shown without the prefix): the stash is full: free space or upgrade (also the Needs-you row "Stash full: free space or upgrade. N kept item(s) wait."; the items STAY queued and the next visit retries; the backpack variant says so), the hero is dead / not in a game (stay queued), this d2d build has no vault verbs (stay queued), the game is busy (stays queued), the game does not accept this item's data (`parse`: failed, back to recorded), another game version (`version`: failed), the created item differs (failed, tripped), the key was already used but the item is not in the hero (`dup`: failed), the save backup / save failed (stay queued). Partial success is normal: items before a failing one are kept, the failing one is marked, the batch goes on after per-item failures and stops after hero-wide ones (stash full, dead, verbs, busy).

Page. The Keep button of the bar and the card are real. The bar has "Keep (n)"; a status row under it shows "Keeping 5 items: arrives at your next town visit" (or why it waits) with "Keep now": it only enqueues (any queued id) and asks the bot for the errand trip home at the next safe moment (`Keeper.TripWanted`, `bot.vaultKeepStep`, same backoff as the other errands); creating still happens in town at a safe moment. Rows show Q (queued), ... (creating), K (kept), ! (failed with the reason in the label, the list and the card); a "Kept" chip in the filters shows `state=kept`.

Live drill checklist (not run; needs the d2d fork with `--vault-verbs`, a throwaway hero, `loot.vault` 1, NO `D2BOT_RUN` for the Keep part and `vault creates: N` declared in the run record, `writes after start: 0` from `d2cheat ledger --since-run`; a Keep run is not a measured run):
1. Start the sandbox hero fresh (zero setup writes), `loot.vault` 1, let it play until at least 20 vault records exist (`GET /api/vault` total).
2. Select 5 on the page, Keep (5): the progress line says "Keeping 5 items", `vault stats` creates stays 0.
3. Let the hero reach town (or press Keep now): expect one `save`, five `item create` lines in the log, rows turn K with `stash c,r`, `vault stats` creates=5, no panel was opened.
4. Reload the game (exit and re-enter): the five items are in the stash, `item full` equals the recorded bytes, unidentified ones are still unidentified.
5. Restart the bot with one item queued: it is created once (vault log shows one `kept`); kill the bot between the create and the save on a second try: no second copy after restart.
6. Fill the stash, Keep one more: Needs-you row "Stash full", item stays queued, free a cell, next visit creates it.
7. Dead hero: press Keep: the toast says the hero is dead; nothing queued.
Record the `.bak` of the hero before step 3 and restore it if anything differs.

### Reveal flow

`POST /api/vault/reveal {ids, now?}` only QUEUES (`Store.RevealWant`, flag `RevQ` on the record). Idempotent (queued: `already`), refusals: `state` (identified, sold, discarded), `noscroll` (more requests than charges, none at Cain), gate codes `off`, `dead`, `verbs`, `stopped`. The page shows the cost BEFORE the click from `GET /api/vault` (`act.reveal`: `charges`, `free`, `perItem`): "Reveal 3 items: 3 charges (free at Cain)" or "...(you have 1): no scroll, buy on request".

Executor (`Keeper.runReveal`, same safe-moment rules, per-visit cap `loot.vaultKeepPerVisit` and 8 s budget as Keep). Per record, each stage logged BEFORE its game step (`Store.SetStage`):

1. `rb`: `item create` of the recorded bytes into the PACK (`key=vr-<id>-<attempt>`), save backup before the first create of the process (as Keep), read-back must equal the record, a mismatch removes the copy and trips the keeper (nothing is created until restart).
2. `rc`: identify the unit (scroll or tome charge, or Cain), read the item back: it must be identified with the same code, quality and item level.
3. The vault record is superseded IN PLACE (`reveal` event: same id, new raw bytes and hash, `identified`, name from the town, value recomputed; no second record). Stage `rt`.
4. `item vault <unit>` removes the temporary copy; stage cleared. No save is needed: the net change in the hero is zero.

Keep and Reveal on one record are ONE flow: the Keep create is made into the backpack (identify works on pack items), identified there, the record is superseded and kept; one create, nothing removed (`TestRevealKeepIsOneFlow`). A Keep+Reveal item therefore lands in the backpack and the stash chore files it (docs/vault.md Keep says stash: this is the one exception).

Failures (stored `reveal: <sentence>`, shown on the row and card): `no scroll; buy on request` (also if the charge disappeared while the request waited: nothing is created), `the game did not identify it: ...`, `the item is still unidentified`, `the game identified a different item`, an identical identified item already in the vault, pack full or hero dead or busy (stays queued), version or bad data. A failed identify removes the temporary copy and leaves the record exactly as recorded.

Restart recovery (`TestRevealRestartAtEveryStep`, 2 classes x keep or not x last call lost or not x 14 cut points): the stage tells what may exist; `resumeReveal` looks at the hero. Copy of the old bytes present: identify it. An identified copy of the same code, quality, level, sockets and ethereal bit that no vault record owns (`adoptable`; ambiguous means none): adopt its bytes. Stage `rt`: remove the copy of the new bytes. Nothing found: the stage is cleared and the request stays queued. After an identify whose reply was lost the hero decides (read back), so a charge is never spent twice. U: two identical unidentified items carried by the hero make "present" ambiguous; the create key and the kept-record count are the only guards.

### Sell-from-vault flow

`POST /api/vault/sell {ids, confirm:true, now?}` (the page asks first in a sheet with the count and the lower-bound price) queues (`sellq`). Refusals: `pinned` (never sold: also enforced in the store, `ErrPinned`, and again by the executor), `state`, gate codes. `POST /api/vault/cancel {ids}` takes a queued Keep, Reveal or Sell back while no step of it ran.

Executor (`Keeper.runSell`, cap `loot.vaultSellPerVisit`, 8 s budget), per record, one at a time:

1. purse read, stage `sb` (with the purse) logged, `item create` into the pack (`key=vs-<id>-<attempt>`), read-back equal to the record (else removed and tripped), stage `sc`.
2. `Seller.Sell`: the created item is marked sell on the inventory desk and the town's own sell chore runs (the same marked-items sale as "Sell now": real vendor, real price, nothing new decides what to sell; the chore also sells the player's own marks, which they asked for).
3. Read-back, in the game: the copy must be gone AND the purse must have grown. Both: `sold` with the gold read from the purse. Copy still there: it is removed again; a refusal by the vendor ends the sale with the reason (`sell: <why>`, record back in the vault), a postponement (fight, busy panel: `ErrPostpone`) leaves it queued. Copy gone but no gold: the record is closed `sold` with 0 gold and a note, the keeper TRIPS (no more sales until restart) and a Needs-you row says so.

Pack full: `the backpack is full`, stays queued, one Needs-you notice per episode. Restart: stage `sb` with no copy in the hero queues the sale again; a copy present continues at the sale; stage `sc` with no copy means it was sold, settled `sold` with the purse change as the gold (`TestSellRestartAtEveryStep`).

## Reveal paid in gold (vaultreveal 2026-11-21, rebuilt as vaultpay the same day; knob `loot.vaultRevealGold`, default 0)

> status: BUILT offline, NOT run against a live game (U). V: `go test ./internal/vaultkeep ./internal/bulkid ./internal/watch ./internal/d2dctl` (orders against `d2dctl.PayFake`, a Paladin and a Sorceress, must-fail tests), node tests of the bar, and the fork test `tests/paygold_d2d.py` on the builder (see the private image note). Tags V (verified how), U (unverified). Decision: [ADR 0029](adr/0029-vault-gold-payment.md) (user popup 2026-11-21, amends ADR 0014 for this one write).

**Mechanism (decision).** A gold reveal is an ORDER the player gives on the Reveal bar. The cost is subtracted from the STASH gold at once, the items are revealed in the same moment: no town visit, no scroll bought, no tome charge, no game step. The first build (task 778, merged as #1071) queued the bot to buy Scrolls of Identify at the next visit; that path is removed (the `bulkid` buy-scrolls chore of the Inventory page stays: it has its own button).

**Price (kept from the first build).** The vendor price of one Scroll of Identify (item `isc`, base cost from the item tables) per item, `heroActs.Price`; no gold figure is written in code. It is a price per item, not a stack of scrolls bought: nothing is bought. The repair and potion reserve of the old design is gone with the purchase: the stash gold is not the purse the town guards read (U: no live check that the guards never withdraw the stash gold mid-order; the payment is one verb call).

**Order (`internal/vaultkeep/gold.go`).** `POST /api/vault/revealgold {ids, maxGold, confirm}` on the answer listener (the same auth as the other vault orders; the page never holds a token). Needs no Reveal gate (like an Ether tap). Steps, all inside the request: (1) refusals: knob 0 (`off`), no payer (`noshop`), measured run (`measured`, D2BOT_RUN), no vault, more than 150 ids; per item: missing, identified (`state`), not in the vault, no held affixes (`nosealed`, the same limit as Ether: gold unlocks the affixes the vault already holds), already unlocked (`already`, never charged twice); (2) price per item `p`, stash gold `s` read fresh from the snapshot: the stash pays for `n = min(eligible, s / p, maxGold / p)` items IN THE PLAYER'S LIST ORDER, the rest answer `gold` with the reason ("short of gold: one reveal costs 80 gold, the stash holds 200"); `n = 0` refuses everything; (3) a cost at or over `loot.vaultRevealGoldConfirm` (2000) needs `confirm:true` (else `confirm`); (4) the order (`queued`, `revealgold.json` next to the vault log, temp file and rename) is saved, the n items are unlocked (`Store.Unseal`, as Ether), then ONE `debug paygold <n*p> <orderid>` is sent through `d2dctl.Pay` (cheat ledger line first, reason `vault gold reveal order <id>`, then the verb); (5) on success the order is `paid`, then `revealed` (or `partial` when n is below the items asked for: "3 of the 5 items you asked for were revealed: the stash paid for those"), with the stash gold the fork answered. A refusal of the fork (stash short, measured run, flag off) takes the unlock back and ends the order `failed` with the reason shown; an unanswered request (a lost reply) leaves it `queued`: the next press or the next town visit repeats the verb with the SAME order id, and the fork answers a repeated id with `paid:0, already:true`, so the gold is never taken twice. `POST /api/vault/revealgold/cancel` ends an order that is not yet paid (practically only after a lost reply). Chain on the page: `queued -> paid -> revealed | partial | failed | cancelled`, seconds; a finished order is shown for 30 minutes with "Stash gold: N".

**The fork verb (private lab fork, flag `--vault-pay`; never upstream).** `debug paygold <amount> <orderid>`: subtracts <amount> from the hero's stash gold stat only if the stash holds it, answers `{"ok":true,"paid":N,"stash_before":A,"stash_after":B,"order":"id"}`; remembers the last 256 order ids (a repeat: `paid:0, already:true`); refuses amount <= 0 or not a whole number, amount above the stash, a measured run (`--lockstep`, or `D2BOT_RUN` / `D2D_MEASURED_RUN` set in d2d's environment at start), and everything when the flag is off (`--lab-verbs` alone does not pay); `caps` lists `vault.paygold` only with the flag. The bot reads that capability (`VaultCaps.PayGold`): without it the Gold option shows "this d2d build cannot take the gold (start it with --vault-pay)". The managed d2d launch (the sandbox compose `--d2d-args`) adds `--vault-pay` only when `loot.vaultRevealGold` is on (U: the launch lives in the private ops repo, not in this one). V: fork test `tests/paygold_d2d.py` (pays from the stash, overdraft and non-positive refused, idempotent repeat, purse unchanged, the state digest differs only in the stash gold, no flag refuses, measured refuses, caps).

**The Reveal bar (page; since vaultclean it is the idle state of the one action bar, see Layout below, and the title and fold are gone).** One bar over the list: "Reveal N items in this filter" (the items the identify filter, `data/bulkid/filter.json`, selects), a payment picker (Free: Cain or the scrolls held; Ether; Gold) with ONE plain cost line per option ("Scrolls: 12", "Ether: 29 of 665", "Gold: 5,800 (stash 7,200)"), one press button with the words of the choice, the skipped items as an expandable "24 skipped" line with the reason per group, the confirm step for a gold cost at or over the threshold ("Pay 5,800 gold from your stash to reveal 4 items?"), and under it the order chain with the progress count, "N gold paid" and "Stash gold: N". The gold option counts only items with held affixes. The default payment is the first of free, Ether, gold that covers every item, else the one that covers most (`bulkid.MakeBar`: the quote is server side, the page only draws it). GET `/api/vault` carries `act.reveal.bar` and `act.reveal.gold` (`on`, `scrollGold`, `stash`, `confirmAt`, `why`, `order`). The per-selection Reveal buttons stay.

**Identify all (identifyall 2026-11-22).** One always-visible toolbar button "Identify all (N)": N is `act.reveal.gold.unrevealed`, the unrevealed records of the WHOLE vault (live, unidentified, not unlocked; no filter, search or selection applies), hidden at 0. ## Gold is the one way to reveal on the Vault page, and it decodes the item's own bytes (vaultid 2026-11-21)

**Why Gold failed for most records, and the fix.** A gold order unlocks the affixes the vault HOLDS (`Rec.Sealed`). A record without them (`Sealed` empty: the recorder of an older build, or a peek that carried none) was refused `nosealed`. But `Rec.Raw` is the item as the save writer wrote it, and that bitstream carries the prefix and suffix ids and the property list even while the item is unidentified (V: `tests/itemdecode_d2d.py`: a magic ring, a rare and a unique long sword and a set cap, unidentified on the floor, carry 2 to 10 properties each; the d2d loot makes them at the drop, `identified` is a separate flag). It creates nothing, touches no unit, hero or RNG state. Differential (the engine identifies the same bytes created in the pack with a scroll, `item identify`): the decoded view equals the engine's view except the identified flag and the inventory colour fields that only `item full` adds, 0 differences on 4 items; the state digest (`dump player,items`, `ground`, `items`, `vault stats`) is equal before and after a decode. Not decodable (U): a record from a game.exe host (a joined or net game): its unidentified item packet has no stat lists (`parse_net_item`), the server holds them; the verb then finds no properties and the record keeps the `nosealed` refusal.

The bar counts every unidentified candidate as gold-revealable when the fork lists `item.decode` (`BarIn.Decode`). The guard rails are unchanged: stash gold only, the vendor price of one Scroll of Identify per item, an idempotent order id, the ledger line before the verb, refused in a measured run, the confirm above `loot.vaultRevealGoldConfirm`, a partial reveal when the stash is short. ## Sell is instant (vaultsell 2026-11-22; knobs `loot.vaultSellInstant` default 1, `loot.vaultSellConfirm` 2000)

> status: BUILT offline (V: `go test -p 1 ./internal/vaultkeep ./internal/d2dctl ./internal/vault ./internal/watch ./internal/scenario ./cmd/d2scenario ./cmd/d2bot`, node tests `vault_logic.mjs`, `vault_sell.mjs`); the fork verbs are V on the builder (see the fork section); the page and the sale against a live hero are U until the scenario `vault.sell-instant` has a verdict. Decision: user, 2026-11-22: "sell should just delete the items from the vault and give you the good value". Management actions are immediate (user decision 2026-11-21); the payment pattern is ADR 0029's (a player-ordered, ledgered, bounded, idempotent fork write), here a CREDIT.

**What changed.** Sell no longer queues for a town visit. The order removes the records from the Vault and adds what the engine's own sell function pays for them to the STASH gold, before the reply. The old queue (sold at the vendor by the town chore) stays as the fallback: knob `loot.vaultSellInstant` 0, a d2d without the verbs below, or no bot wiring. Orders the player gave under the old queue (`sellq` with the ordered flag) are paid at once by the next `Run` when the instant sale is on (`flushQueued`); marks (no order) are never touched, the "Marked for sale: N" list and its "Sell these N now" button use the same instant path.

**The value (decision).** The engine's price, not a floor. The fork's read-only verb `item price <hex> [npc]` runs `d2d::rules::item_price` (sell side, the port of game.exe FUN_0062efb0: base cost, armor defence, quality extras and the stat cost of identified magic, rare, set and unique items, sockets, ethereal and class quarters, the NPC buy mult, the max buy cap of the hero's difficulty). It answers `price npc=<id> sell=<as recorded> sell_id=<as if identified> was=<0|1>`. The bot pays `sell_id` for a record the player has revealed (identified, or unlocked by a gold reveal: an identify scroll would do the same) and `sell` for an unidentified one (the engine pays only the base for those, so the bot never pays more than the game would). Vendor: the verb's default `akara` (npc.txt sell mult 1024 and the Act 1 max buy), so the price does not depend on which town the hero is in; the real vendors differ by their own mult (Charsi 960, Gheed 1088, Act 5 2048, S from docs/research/price-trace.md). Never above the engine's value; the Vault tooltip's "Sells for at least N" stays a floor from the tables and the sheet of a sale shows the engine's number. If the verb is missing the instant sale is off (the floor is not paid). The bot caches a price per record bytes and identified flag.

**Order (`internal/vaultkeep/sale.go`).** `POST /api/vault/sellquote {ids}` (answer listener, changes nothing) answers `{asked, count, lines[{id,gold}], total, stash, stashAfter, room, reasons[{code,n,why}], confirmAt, needConfirm}`. `POST /api/vault/sell {ids, confirm:true, ack}` runs the sale when the bot says it can (`act.sell.instant`): (1) refusals per record: `missing`, `pinned` (the existing rule, never sold), `state` (sold, kept, discarded, in the keep queue), `busy` (an old reveal or sale step in flight), `price` (the verb failed), `room` (the stash would pass 2,500,000: the first records that fit are sold, in the player's order, the rest answer `room` with "the stash holds X of 2,500,000: room for Y more"); (2) a total at or over `loot.vaultSellConfirm` needs `ack:true` (else `confirm`, nothing happens); (3) the order (`sale.json` next to the log, temp file and rename, state `queued`) is saved; (4) ONE `debug creditgold <total> <orderid>` through `d2dctl.Pay.CreditGold` (cheat ledger line first, reason `player vault sale order <id>`, params amount and item count, then the verb); (5) on success the state is `credited` and each record is archived (`archive.jsonl`, reason `sold: G gold, order ID`) then marked sold (`Store.SellNow`, event `soldnow`), the order ends `done` and the reply carries `sale {state, items, done, gold, stashBefore, stashAfter, line}`. A refusal of the fork (room, measured run, flag off) ends the order `failed` and EVERY record stays in the vault; an unanswered request (a lost reply) leaves it `queued` and the next press or the next `Run` repeats the verb with the SAME order id (the fork answers a repeated id with `credited:0, already:true`); a restart after `credited` finishes the removal without a second credit. ## Decision 2026-11-21: a full Vault never removes anything

User decision (the Ethereal Vault, sandbox hero): "we shouldn't sell items when it's full, just don't record drops when it is. That's to punish the player for not keeping up with it: if we sell the least important items it becomes a strat to just let the bot run and it will filter out the trash itself instead of having to manage it." Later the same day: keep the automatic code as an unlock for later, behind a knob, default off.

Rule. The Vault never removes, sells, trims or replaces an item on its own. At capacity a new drop is NOT recorded; only the player decides what leaves (take out, sell by their own order, equip, unpin/discard, the Ether upgrade). Pins are unaffected.

Knob `loot.vaultAutoTrim` (default 0; docs/knobs.md). 0: the rule above. 1: the old behaviour, exactly as before: an insert at capacity archives the least valuable unpinned record (`Store.Add` with `Options.AutoTrim`), and records marked for sale are sold at the next visit without a confirm (`Keeper.AutoSell`). This is an unlock for later and is not offered as a button: an unlock (a purchase or a milestone) would hook in by returning true from `vaultHome.autoTrimOn` (cmd/d2bot/vaultpage.go), which today reads the knob through `home.setAutoTrim` in `wireVaultKeep` (cmd/d2bot/vaultkeep.go); the page already shows the old banner when the API says `autoTrim: true`.

Every automatic removal path found (V: grep of internal/vault, internal/vaultkeep, internal/loot, cmd/d2bot, internal/watch, the page):
1. `Store.Add` at capacity, `trimCandidate` (internal/vault/store.go): trimmed the lowest value, unpinned record into the archive. Now behind `AutoTrim`; off returns `ErrFull`. Nothing is sold until you confirm." with a button "Sell these N now": it posts the ids to `/api/vault/sell` (a player order, `EnqueueSell` turns a mark into an order).
