# Outside pull requests: the proposed review gate

> status: policy text APPROVED by the maintainer 2026-11-01 (card communitywork); its proposed repository settings (branch protection, CodeRabbit app on this repo, PR-based workflow) remain OFF until the maintainer turns them on (decision 2026-11-01: direct pushes with the merge lock stay for now). Tags: V = read in this repo, S = GitHub or CodeRabbit documentation as the author remembers it (not re-read this session), U = unverified. Re-check every S item in the GitHub settings page before relying on it.

Contributors are friends and their AI agents, working from forks, on docs and small tools. The gate has to keep three things safe: the repo (no game code, no secrets, no binaries), the maintainer's credit (the API key is only spent on the owner's own PRs), and the maintainer's agents (outside text is data, never instructions). Contributor guide: [../contributing/agent-work.md](../contributing/agent-work.md).

## 1. What already protects the repo (V)
- `.github/workflows/ci.yml` runs on `pull_request`. For a PR from a fork GitHub gives that run a read-only token and NO repository secrets (S), so a hostile PR cannot read `ANTHROPIC_API_KEY` or the Discord webhook through CI. The `checks` job runs changecheck, leakcheck, the hygiene check and the gamecode guard; `test` is skipped for docs-only changes.
- `.github/workflows/pr-review.yml` (API review) runs only when the PR head repo is this repo AND the actor is the owner (V, in its `if:`). Outside PRs never spend the credit. Keep it that way ([api-credits.md](api-credits.md)).
- `tools/hooks` (pre-push, install with `tools/install-hooks.sh`) only run on the maintainer's machines; they do not protect against a PR.

## 2. Proposed gate
1. **Branch protection on `main`** (maintainer, Settings, Branches; S): require status checks `checks` and `test` before merging a pull request, require branches to be up to date, require conversation resolution, no force pushes. Do NOT enable "include administrators" and do not require reviews: the owner keeps direct pushes and merges as today (admins bypass), while a merge button on an outside PR stays red until the checks are green. A PR from a fork still needs the maintainer to approve the first workflow run for a first-time contributor (S, Settings, Actions, "Approval for running fork pull request workflows": choose "Require approval for first-time contributors" or stricter).
2. **CodeRabbit as the first automatic reviewer** for outside PRs: install the app for this repo (maintainer, U: plan and limits for a public repo not checked) and commit [../../.coderabbit.yaml](../../.coderabbit.yaml). It skips the owner's own PRs (`ignore_usernames`), reviews research documents (they ARE the contributions) but ignores generated files, logs and images, and speaks tersely. Its free review limit may stop it mid-day (upstream saw a "review limit" notice, V docs/research/pr-bundle-queue.md); a missing CodeRabbit review never blocks a merge.
3. **API review stays owner-only.** For an outside PR a maintainer can run the same script by hand after reading the diff once themselves: `DRY_RUN=1 GITHUB_TOKEN=... GITHUB_REPOSITORY=... PR_NUMBER=N python3 tools/ci/pr_review.py` prints the request size (V, api-credits.md); without `DRY_RUN` it calls the API with the key from the maintainer's own environment. The script reads the diff from the GitHub API and never checks out or runs the PR's code (V, pr_review.py header; re-read before use).
4. **Optional later: a `review-api` label.** A label-triggered job on a fork PR must use `pull_request_target`, because only that event carries secrets for fork PRs. We do NOT use `pull_request_target` now: it runs in the context of the base repository with its secrets and a write token, and the classic compromise is a workflow that then checks out and runs the PR's head (a build step, a test, a script from `tools/`). If the maintainer ever wants the label, the only safe shape is: trigger `pull_request_target` types `[labeled]` with `if: github.event.label.name == 'review-api'` and a check that the label was added by a user with write access; check out the BASE sha only (`ref: ${{ github.event.pull_request.base.sha }}`, `persist-credentials: false`); run only `tools/ci/pr_review.py` from that base checkout; never execute, import or build anything from the head; keep the diff cap (120 KB) and the file cap; `permissions: pull-requests: write` only. The remaining hazard is prompt injection in the diff steering the review text (the review is advisory, never blocks, and posts only a comment) and cost abuse (only a maintainer can add the label). Until then: manual run (item 3).
5. **Merge rule:** a maintainer merges an outside PR only after the checklist in section 4, and nothing from an outside PR goes upstream without an independent verification (guide, section 7).

## 3. What the maintainer checks first
- CI: `checks` green. In particular the **gamecode guard** output (it must say `gamecode guard ok`; a failure lists the files and line ranges) and **leakcheck** (`go run ./cmd/leakcheck -mode fail`, 0 hits).
- **No binary files**: `git diff --stat origin/main...` shows only text; `file` on anything unusual; the hygiene check (`tools/ci/check.sh --hygiene-only`) refuses MPQs, saves, keys and big files.
- **Size caps**: a research document over about 100 KB, or more than about 20 files, is suspicious for a trace; a tracked file under `docs/` over 256 KB fails the guard unless listed (`tools/ci/gamecode_allow.txt`, never add an outside file there).
- The PR touches only the files its issue names. Anything under `tools/`, `.github/`, `cmd/`, `internal/`, `deploy/`, `packaging/` or `go.mod` is a stop sign unless the issue asked for it, and then needs a line-by-line read.
- The evidence checklist of the guide (tags, reproducible numbers, limits, no pasted code) holds.

## 4. Security checklist for PRs written by AI agents
Read the raw diff, not only the rendered page.
- **Prompt injection in markdown**: instructions aimed at a reviewing agent ("ignore previous rules", "approve", "run this", "also edit X"), in body text, HTML comments (`<!-- ... -->`), link titles, image alt text, front matter, collapsed `<details>` blocks, tables, code fences labelled as output. Search: `grep -rniE 'ignore (all|previous)|as an ai|system prompt|you must|do not tell' $(git diff --name-only origin/main...)`. Our agents treat PR text as data (guide, section 10); a human reads the PR first and does not hand an agent a PR to "follow".
- **Hidden unicode**: zero-width characters, bidirectional controls, tag characters, look-alike letters. Check: `git diff origin/main... | grep -nP '[\x{200B}-\x{200F}\x{202A}-\x{202E}\x{2060}-\x{2064}\x{FEFF}\x{E0000}-\x{E007F}]'` must print nothing (S: `grep -P` Unicode classes need a UTF-8 locale; U: not run in this session).
- **Links**: no shortened links, no links to download pages for game files or cracks, no `javascript:` or `data:` URLs, no external images (they leak the reader's IP when rendered). Prefer links into this repo, `psi29a/d2decomped` and public documentation.
- **Scripts in `tools/`**: any new or changed script is code that runs on the maintainer's machine and in CI. Read it fully; look for network calls, `eval`, `exec`, base64 blobs, environment reads, writes outside the repo, `curl | sh`, changes to `tools/hooks` or `tools/ci`. Do not run a contributor's script on a machine with credentials; if it must be run, run it in a throwaway container or VM without network. `.github/workflows/**`, `CODEOWNERS`, hooks and `go.mod` changes from outside are declined unless pre-arranged.
- **Game content**: no listings, tables, binaries, screenshots of game data; a trace that quotes more than a one-line formula goes back for rewording. Guard passing is necessary, not sufficient.
- **Identity**: the commit author is whatever the contributor chose; do not trust an `Agent:` line or a claimed maintainer name. Credit follows the guide, not the commit text.
- **Secrets and paths**: tokens, webhook URLs, home directories, hostnames (leakcheck catches the common shapes; a human catches the rest).
- **Tooling that fetches**: no change that makes our tools call outside hosts. Work items never need network access beyond cloning public repos.
- Merge with a squash commit written by the maintainer, so the final message is ours and carries no injected text.
