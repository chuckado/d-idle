## 3 update 0.1.1 to 0.1.2 (V)

Real 0.1.1 pack, non-DEV image, feed override in `docker-compose.override.yml` (`D2BOT_UPDATE_FEED` set to a local https name, `SSL_CERT_FILE` pointing at a throwaway CA mounted into this one container, `extra_hosts` to the host). The feed was a copy of the staged feed tree (URLs rewritten to the local name) served by a small https server; the private pack URL was never used. Keys were the baked ones: the signed set `app-v0.1.2` seq 3 was accepted.

`./didle update` (pty, answer y) with a level-1 hero fighting: "release 0.1.2 is available", download ok (state `ready`, hash and signature checked), apply refused `not-safe` ("the hero is not in a safe spot"), as the 0.1.1 client is designed. Retrying apply every 5 s: accepted at the 8th try (hero between fights), container restarted, `didleboot: starting release 0.1.2 (base=false pending=true)`, `d2bot start version 0.1.2`, same Paladin reloaded at level 2. `./didle status`: `running release: 0.1.2`.

Finding (0.1.1 and 0.1.2 `didle`, same block): after the apply refusal the wrapper still prints "applied: the bot restarts on 0.1.2". Cosmetic; a friend must read the JSON line above it. Proposed small card: have `./didle update` check `"ok":true` before printing it.

## 4 rollback (V)

Right after the update (inside the 10 minute probation): `POST /api/update/rollback`. Log: `didleboot: rolling back 0.1.2 to "": exited with code 0 before it was confirmed healthy`, then `starting release 0.1.1 (base=true)`, same Paladin level 2 reloaded; `./didle status`: `running release: 0.1.1`, update state idle, container restarts 1. The `to ""` in the log line means the base image release (the target is the image's own 0.1.1); the wording is odd but the result is right.
