# Bot CPU bursts in town walks (card botcpu, 2026-11-16)

> status: partial. Offline profile only; the live repair-trip profile is a checklist (section 4). Trigger: docs/video-feed.md section 11
> (bot at 64 to 71 percent of the one-core quota for 10 to 47 s, 67 to 87 s apart, against 15 percent calm).

## 1. Method (V = measured here, on the head box, an Intel N95, so absolute times are slow-box times)
No game, nothing on the sandbox (it had just restarted; no heap or CPU profile files were in its data volume). Three benchmarks, all
`go test -p 1 <pkg> -run XXX -bench <name> -cpuprofile f`, then `go tool pprof -top`:

| Benchmark (file) | Scenario |
|---|---|
| `nav` `BenchmarkTownTour` (cpuprobe_test.go) | simulated walk on the recorded Rogue Encampment (both fixtures): Charsi, stash, Akara, waypoint, Gheed; the sim clock only moves when nav sleeps, so wall time is pure nav CPU |
| `d2dsrc` `BenchmarkReadLate` | one full 8-verb snapshot (late-game character, item dump parsed) over a unix socket |
| `senses` `BenchmarkObserveWalk` | the OnObserve hook's `Publisher.Observe` for 100 subtiles of walking in the same town |

## 2. Findings (V)
Per second of town walking (9.4 polls, 2.1 clicks per second in the sim):

| Part | Cost | Share of one core |
|---|---|---|
| nav walk loop + planner (`TownTour`) | 0.3 ms per walking second (the 48 ms field build is once per level) | 0.03 % |
| snapshot decode (`Source.Read`, 68 KB and 1015 allocs per call; 41 % is `encoding/json` into `map[string]any`) | 0.29 ms x 9.4 = 2.7 ms | 0.3 % |
| `senses.Publisher.Observe` map rebuild, BEFORE | 0.65 ms per subtile walked: the whole grid rescanned with one map lookup per cell (75 % of the samples are `Observe.func1`, `mapaccess`) each time the hero reveals a new 4-subtile block | 0.6 % in town, scales with level area (outdoor levels are 10x larger) |
| same, AFTER | 0.16 to 0.20 ms per subtile (dense block array, fog tested before the grid flags) | 0.15 % |
| `coverageFor` + `SetCoverage` | copies every roam point twice on EVERY poll (10 Hz), unthrottled, while the minimap map is throttled to 2 Hz | not in town (no roam grid); an allocation burst per poll on a roam level |

Conclusion (V for the numbers, U for the cause of the sandbox bursts): in the offline town walk nothing reaches even 1 percent of a core.
The 65 percent bursts are NOT explained by nav, snapshot decoding or the minimap in town. What the offline numbers do say: the only part
of the walk that costs real CPU per poll and grows with the level is the senses map rebuild, followed by the unthrottled roam-coverage
copy. The burst cause has to be in something the sim does not run: the repair trip itself (the town verb paths, `d2dinput` hover
waits and kicks, `Loot` and tidy passes, minute logging) or CPU spent by the 1-core container's own scheduling (a Go process that is
throttled for 90 of every 100 ms shows its few runnable goroutines as busy for the whole period).

## 3. Fixes (behaviour unchanged)
1. `senses.build`: fog lookup from a dense block array (`fogLookup`) and the fog test before the grid-flag read. `TestFogLookupMatchesMap`
   proves the same answers as the old map lookup inside and outside the bounds; the existing senses tests (map RLE, neighbours) pass.
   Walk benchmark 64.8 ms -> 15.8 ms per 100 subtiles (4.1x), same allocations.
2. `cmd/d2bot` `coverageThrottle`: the roam coverage is pushed to the minimap at most every `sensesEvery` (500 ms) and at once on an area
   change; single-cell flips still go at once through `SetOnCoverChange`. `TestCoverageThrottle`. Display-only data.
Two builds: neither change reads a class, skill or build; nothing build-specific.

## 4. Live checklist (needs the sandbox or a lab d2d; not run)
The bot already has a CPU profiler: `D2DCTL_PPROF=/path/cpu.prof` (internal/d2denv/env.go `cpuProfile`) writes a 30 s CPU profile 20 s
after start plus `/path/cpu.prof.stacks` (50 ms wall-clock goroutine samples). It starts once, so start the bot, then arrange the repair
trip inside that 20 to 50 s window (damage the armor through the setup path, or set the repair threshold so the first town visit
repairs), then `go tool pprof -top -cum cpu.prof` and `grep -c` the top frames of `.stacks`. A second pass with `D2BOT_NAV_TRACE`
off tells whether the 10 Hz `nav.trace` lines (slog text, one `Info` each) matter. Run it niced, in the sandbox only with the user's go.
