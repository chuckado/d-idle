# Automatic Allocate Skills, the gold respec and the currency consolidation (design, 2026-11-21)

> status: DESIGN plus a built first slice (agent autoalloc). Tags: **V** verified (how said), **S** secondary, **U** unverified. Nothing here ran against a game. Source: user request 2026-11-21 (Automatic Allocate Skills button, build picker, lock-in, gold respec, "fuel all our meta currency needs with Gold and maybe Runes") and the popups: the respec price scales with level and with each respec of that hero, the respec refunds skills AND stats, the build is LOCKED until a gold respec is paid. Clarification the same day: respec NUMBERS are deliberately not decided; only the model and the knobs are. Proposed decision text for the coordinator is at the end (this file edits no ADR).

## 1. Automatic Allocate Skills (built, knob off)

**What the player sees** (Points page, `/watch/points`, card "Automatic Allocate Skills"). A button opens the picker: every build file of the hero's class, each with its tier label, the skills it needs that the fighter cannot use well yet (warned, not hidden), and a collapsible preview of the first 30 levels (skills and stat points per level, each skill tagged with its capability tier). "Choose and lock" asks once ("Lock to X? Every new point follows it. Changing it later means a respec, about N gold now, that refunds all skill and stat points"); an experimental build asks a second time. Locked: the picker button and every choose button are disabled, the card says "Locked to X since level N. Respec to change" and the respec line reads "A respec now would cost N gold ... Respec: coming soon" (button disabled; V built, `internal/watch/web/points.js`). The Skills page gets only a link (not edited: another agent owns it; a card in section 6).

**Data (V, built, `internal/points/store.go`).** The hero plan file is `<hero>.points.json` (the points settings file; additive fields, readers of the old file see "no build"): `build`, `locked`, `lockedAtLevel`, `lockedAt`, `respecs` next to `autopilot`. Written atomically; a stored lock survives a restart (test `TestSetBuildLocksAndRefusesSwitch`).

**API (V, offline tests).** `GET /api/hero/build` (viewer): class, level, `autoAlloc` (the knob), `state`, `builds[]` with `tier`, `needs[]`, `preview[]`, `held[]` (points the allocator did not spend, with the reason), `offBuild[]`, `respec {price, available:false, note}`. `POST /api/hero/build {"build": name, "confirm": bool}` on the answer listener (token, origin list, JSON only, audited like the points POSTs): ok; same build again ok with `already:true` (idempotent); unknown name 400 `unknown_build` naming it; another class's build 409 `other_class`; another build while locked 409 `locked` ("locked to X since level N; a respec (P gold) is the only way to change it"); an experimental build without confirm 409 `confirm` + `needsConfirm`.

**Tiers.** A build's tier comes from the capability table (`data/capabilities/capabilities.json`, tier computed by `internal/delivery`): **experimental** when any skill of its first 30 levels is an attack or summon the fighter has no engine support for (`unsupported`), else **supported**. Every other skill that is not `supported` (utility, movement, merely unproven) is listed in `needs[]` as a warning but does not change the build tier: nearly every real build contains an unproven skill (V: of 13 shipped Paladin and Sorceress tables only the Lightning ones are experimental, `TestAllocBuildListTwoClasses`). The capability data is the single source; no skill or class name is in Go.

**At each level-up (V, `Desk.AutoAllocOnce`).** Every 3 s while knob `agency.autoAlloc` is 1 and a build is locked: calm moment only (the points desk's busy rule), then the planner (`leveler.Build.Plan`, the same one the leveler uses, so quest-point pull-forward and "owned counts against the table" are inherited) lists the remaining steps, stats first. The desk spends the first spendable one through the existing `SpendStat` / `SpendSkill` (legality check, verb, read-back), one point per tick, and logs `auto-alloc: clvl N -> skill X (build B)`. Idempotent across restarts: the plan is derived from what the hero owns, not from a counter.
- A skill the legality check refuses with "ask" (an unsupported attack): the point is HELD, the next step is tried, the reason shows on the page ("Held for you, spend it on the Skills page to confirm") and the point stays banked (bank-and-ask, ADR 0020). Any other refusal is a visible reason too. An experimental-tier skill of a build the player confirmed is allowed without asking.
- When the table runs out (the normal30 tables end at 30) the points bank and the Needs-you row shows (existing). A staged hand-off to an endgame table is a later card.
- **Interplay with the gate.** `resource.pointsDecisions` and the hero autopilot still mean "the leveler spends from the config table". While the allocator is on AND a build is locked, the points gate is closed for the leveler (`Desk.Locked()`), so the two never double-spend; the allocator is the spender. Knob off or no lock: nothing changes.
- **Manual spends while locked: allowed.** The hero's own `+` presses still work. A skill the build's table never buys shows as "off-build" on the card; because the plan counts owned points against the table, the allocator reflows around the manual point (it simply has one point less to place). Nothing undoes a manual spend; only a respec does. Recommendation, not a rule the code enforces.
- The combat profile does not follow the lock in this slice (the fighter keeps its own choice, as with every build today); card C6.

## 2. Respec (design; the pay button is disabled until the fork card exists)

**Price model (V as code, `points.RespecPrice`; numbers are PLACEHOLDERS, deliberately not decided).** `price = clamp(minGold, maxGold, baseGold + perLevel x clvl) x (1 + perRespecPct/100 x paid respecs)`; the first `firstFree` respecs of a hero cost 0 and do not count for the escalation (this is the "first one cheap" knob; 0 free by default as a placeholder, the recommendation is 1). Knobs, group `respec` (registered in the normal registry, so they are in `docs/knobs.md` and in the dashboard's knob list under a "respec.*" section with plain-English text): `respec.baseGold`, `respec.perLevel`, `respec.perRespecPct`, `respec.firstFree`, `respec.minGold`, `respec.maxGold`. The numbers (500, 250, 50 percent, 0, 1000, 100000) only make the preview look sane. **Discoverability:** the formula is in each knob's text; the live "a respec now would cost X gold" line is on the Points page (computed from the live knobs and the hero's level and respec count). A preview inside the dashboard's generic knob screen needs a UI card (C11); today the dashboard shows the knobs and their texts, the price preview is one tab away.

**Refund = all skill and stat points.** What the ENGINE can do: the game already has the exact reset. Akara's gossip line `Reset Stat/Skill Points` exists on d2d (V `docs/d2d-spike.md` section on NPC dialog, Akara index 4 lists it); in 1.13+ it is free once per difficulty and the Token of Absolution recipe repeats it (S: review 04 section 3.7; the free-once rule is U on d2d). The reset returns both skill and attribute points (S: Akara/Token behaviour; U on d2d). The fork should call THAT handler, as a verb-like command (working name `cmd respec`), not edit memory. The fork checkout was not available to this agent, so the handler name and its count-per-difficulty bookkeeping are U: the fork card must find the d2d NPC reset handler and its once-per-difficulty counter. A card must do, in the fork: (1) expose the handler as `cmd respec` behind a flag (`--respec-verb`, off by default, in `caps` only when on, same pattern as `--vault-pay`); (2) bypass the NPC range/dialog and the once-per-difficulty gate for a PAID respec (the gold is the gate; the free Akara one keeps the game's own count), or explicitly not bypass if that is what d2d's handler enforces: report which; (3) refund skills AND stats, fire the game's recalculation (life/mana/stamina, skill levels at 0, unspent counts), leave items and equipped gear untouched (items that no longer meet Str/Dex stay worn like in the game); (4) answer `respec ok skillpts=N statpts=N`; idempotent by order id like `paygold`; (5) refuse in lockstep or when `D2BOT_RUN` names a measured run; (6) a headless differential that proves unspent = old spent + old unspent.

**Sequence (bot side, the card after the fork card).** `POST /api/hero/respec {"confirm": true}` on the answer listener: 1. refuse `no_lock` if nothing is locked (nothing to respec; the manual route is Akara); 2. refuse `fight` when hostiles are near; 3. read stash gold, refuse `short` with the price and the gap (never takes purse gold: same rule as ADR 0029, bounded to the stash); 4. refuse `measured_run` when `D2BOT_RUN` is set; 5. `paygold price <orderid>` (ledger line written before, reason `respec order <id>`); 6. `cmd respec <orderid>`; 7. read back: unspent points equal the old total, every hard point 0; 8. `Store.ClearBuild` (lock off, `respecs++`), log `respec: paid P gold, refunded S skill and T stat points`; 9. the page tells the player to pick again. Failure after 5 and before 6 (verb refused or process died): the payment is idempotent by order id and the order is replayed at the next tick until it succeeds or the player cancels; if the verb can never run (no flag) the gold is NOT paid, because step 6 is checked with `caps` BEFORE step 5. Mid-quest is allowed (no quest state depends on skills). In a fight it is refused. Not enough gold is refused with the number.

**UI confirm (V text built, pay disabled).** "Respec now? This refunds all N skill points and M stat points, unlocks the build X, and costs P gold from your stash (you have S). You will have to choose a build again." Two taps, price in the button.

**Free Akara respec:** a player may also use Akara's own reset in the game (not through us). Recommendation (open question 2): treat "all hard points are 0 while locked" as an external respec, clear the lock, `respecs++` without gold, so the lock never wedges.

## 4. Consolidation proposal: GOLD for management, RUNES for commitments

**Principle.** The player-paid costs are paid in things the game already has and the hero already farms, so the idle loop IS the economy and nothing is a second ledger the player has to learn.

- **GOLD (stash gold, paid by `debug paygold`, instant, ADR 0029 family):** every repeatable management action: respec (section 2), vault Reveal (done), vault capacity tiers (replaces Ether prices; a one-time purchase per tier, gold price from data), later build-switch conveniences. Thematic: gold is what Akara, Cain and the town charge.
- **RUNES (physical items, paid by the drop verb, no memory write):** one-time COMMITMENTS and unlocks that should feel earned: a tier-2 unlock such as a second build slot per hero, a second Vault tab, an extra Hall of Fame title, a free-respec token. Paying means the hero stands in town and drops the named rune(s); the item is left on the ground (a "sacrifice"). Thematic: runes are the game's own prestige currency and are also wanted for runewords, so spending them is a real choice (the sacrifice competes with a runeword; that is the point). Mechanism: an order with an id, the bot finds the rune in the pack or stash, uses the merged `item drop` verb, verifies the item left the inventory, writes a ledger line keyed by the item unit uid (a replay cannot pay twice), and the loot rules get an `ignore` entry for that uid so the bot does not pick it back up (without it the bot would; this is the one real risk, tested by a scenario).
- **Ether:** stop issuing new Ether sinks. Keep the earn side as RENOWN (a score and a title ladder, not spendable): quest, first, boss and milestone rows keep paying because they are the once-only, non-farmable record of play. Its sinks move: vault capacity tiers become gold prices (data, from `data/vault/capacity.json` with a gold column), tier-2 unlocks become rune prices.
- **Tally and Raven's Mark:** unchanged for now (Tally is the pacing price of the fun loop, ADR 0018; the Mark stays deferred). Re-examine once gold and runes carry the sinks: the likely end state is Tally = the expedition ledger only.

**Mapping of existing Ether flows.** Capacity tier price N Ether -> gold price (data column, placeholder: 1 Ether = 500 gold, so 20 Ether = 10000 gold; U, set by the simulator, C13); `Downgrade` refund -> a gold refund is a write the wrong way (adds gold: forbidden, section 5): refunds are dropped; tiers become permanent purchases. The capped kill trickle goes away (gold already flows from kills).

**Migration of existing Ether balances (the sandbox hero has 665).** One-time conversion, no write that adds anything: convert each balance into the thing it would have bought. 665 buys capacity tiers v1..v5 (20+40+80+160+320 = 620, 45 left): grant those five tiers as owned (data, grandfathered, the ledger line `migrate/ether-to-tiers` keyed once per account), and turn the 45 left into one free respec (`respecs` offset / `respec.firstFree` for that hero) because a respec is the thing the user wanted gold for. A balance below the first tier price converts to nothing but the Renown score. The conversion is a ledger entry type, replay-safe like the rest. Alternative (open question 5): convert at the gold rate and deliver nothing, which is wrong because adding gold is a write the other way.

**Exploit and abuse analysis.** Can the bot farm gold and runes to buy meta power? Yes, and that is the intended loop (an idle game). Keep it fun and bounded:
- Everything bought is convenience or capacity, never combat power: no purchase adds stats, levels, XP, skill points, items, monsters, drop quality or luck. A respec only reallocates points the hero already earned.
- Prices scale: the respec escalates per respec and with level; vault tiers have a price ladder with a hard top (v6). Target (U, set by the simulator): a meta purchase every few hours of play, never faster than the gold the bot needs for kit and repair (the existing poverty and recovery rules protect that: a hero that spends its stash on a respec and cannot buy potions is the failure to avoid; the pay step refuses below `resource.reserveGold` plus the minimal kit cost).
- Stash gold only, never purse; and the stash gold ceiling of the game bounds the biggest price (S: 2,500,000 in 1.14d; `respec.maxGold` is far below it).
- Gold farming as the optimum: the bot's Farm gold order already exists; the fun risk is "everything is a gold farm". The mitigation is price shape (respec escalation), not a ban: farming for a respec is a legitimate player choice.
- Measured runs: never pay (the CRUTCH RULE of ADR 0014 is unchanged; the same `D2BOT_RUN` refusal as `paygold`); `writes after start` counts a paygold as a write, so a measured run that paid is CHEATED by definition and the code refuses before that.
- Replays and double pay: every payment is idempotent by order id (gold) or item uid (runes).

## 5. What must NOT be currency

Anything that turns the bot into a cheat or breaks fidelity: stat or skill points, levels, XP, item stats or rerolls, monster or drop-rate changes, free items from nothing (no verb ever ADDS gold, runes or items: payment is subtract-only), Magic Find or luck, and any purchase inside a measured run. Never the purse gold (the hero's potion money). Never an unbounded write: a paid write is bounded by the stash, idempotent, off by default behind a fork flag, logged before it is sent (ADR 0029 guard rails; the respec verb is the same family). Never spending that bricks a hero without warning: the confirm names what is lost.

## 7. Open questions (recommendation first)

1. **Does the paid respec bypass the game's once-per-difficulty gate?** Recommend yes for the paid path (the gold is the gate), no for the free Akara path; the fork card reports what d2d's handler really enforces (U).
2. **What if the player uses Akara's own reset while locked?** Recommend: detect "all hard points are 0 while locked", clear the lock, `respecs++`, no gold. Else the lock wedges.
3. **First respec cheap:** recommend `respec.firstFree` = 1 and the migration free respec on top; the numbers stay placeholders until C13.
4. **Should respec be capped per hero?** Recommend no cap; the escalation is the limit.
5. **Ether migration shape.** Recommend grandfathered tiers plus a free respec (no write adds anything). Needs the user's nod because it changes what 665 Ether means.
6. **Locked build and the combat profile (C6).** Recommend yes: a build is a skill table AND a combat line; today only the table follows the lock.
7. **Table end (clvl 30).** Recommend banking and a Needs-you row, then a staged endgame hand-off card; never silently switching builds under a lock.
8. **Purse gold for respec if the stash is short.** Recommend no: stash only, with a hint "deposit gold" (the purse is the potion money).
9. **Ether name.** Recommend Renown for the score; keep "Ether" only in the migration text.
10. **Rune prices:** recommend low runes only (El to Ort tier) for the first unlocks so the loop never needs a rare rune; the exact list is data, set with C9.

## 8. Proposed decision text (for the coordinator; not written here)

"2026-11-21 (user, popups): Automatic Allocate Skills follows a chosen build file and the build is locked until a gold respec is paid; the respec refunds all skill and stat points; its price scales with level and with each respec of that hero, numbers not decided (knobs `respec.*`). Meta currency consolidates on stash gold (paid by the player-paid write family, ADR 0029) and runes (paid by dropping them); Ether stops being spent and becomes the Renown score. Respec is a reallocation, not power, so it is outside the F7 rule against permanent power for currency."
Proposed ADR 0029 amendment: "The player-paid write family also covers the paid respec: `debug paygold` for the price and the fork's respec verb for the reset, same guard rails 1 to 7 (player order only, never in a measured run, bounded by stash gold, idempotent by order id, logged first, off by default behind a fork flag)."
