## Verdict: PASS WITH CHANGES (not postable as is)

The rule is right, and much better supported than the author says. game.exe sends a clicked warp down the same unit-target walk as an item, an NPC or a monster (V read). On real map data d2d's unit plan equals game.exe's path in **every one of 61,245 starts** I ran (three sweeps, all five acts, 5 distances x 16 directions), while the spot plan differs in 1,012. The author's sweep covered **Act 1 only** (levels 1..39), not "every Act 1 to 5 warp". Over Acts 2 to 5 the fix moves the outcome from **117 mismatches to 1** (116 fixed, 0 new), so "thin, one combination of 324" came from the level range, not from the rule.

The PR as built cannot be posted. The ctest test asserts nothing (it passes with or without the fix). The committed `compare` cannot tell the parent from the claim. The outcome check that does exist is not in the PR. The oracle commit comes after the claim. The body is a sketch, and its "every Act 1 to 5 warp" and "0 after" are not what the evidence shows. The required changes are below; none touches the one-line rule.

## Non-warp unit targets and other callers (V read)

- The change is `plan_unit = to_unit || actor->take_warp >= 0` in the one `player_walk` call of `World::tick_level` (`tick.cpp:588`). `to_unit` is already true for an NPC, object, door, chest, shrine, portal (`interact_npc`, `take_portal`) and a monster (`fight.engage`), so for those `plan_unit == to_unit`: **no change**. The re-plan rule (`off > 5` against `!= 0`) and the end-of-walk re-path still use `to_unit`, so a warp keeps the spot re-plan and the single server re-walk (`walk_pending`), as before.
- `take_warp` is set only by a click inside a warp's Select box (`commands.cpp:675-680`; also reached by a Pickup or Resurrect walk whose point lies in a warp's box, a pre-existing oddity: the target then becomes the warp unit) and by an operated trap door (`objects.cpp:600`, the door's room's warp). For the trap door a walk, if one follows, is now planned as a unit walk to whatever `target_x/y` holds (U, a rare path, not tested upstream).
- Upstream tests touching warps: `test_warp_arrival` sets `take_warp` and calls `use_warp` directly (no walk); `test_warp_click` tests `warp_clicked` only. Neither is affected (V read); ctest table above.
- Sibling deviations seen on the way (not this PR; follow-up candidates): an item pick-up is the same unit-target walk with **near 2** (`0x64992b`) while d2d plans it as a spot walk (`to_unit` false for `pick_item`); objects get near 2 or `FUN_006497d0` where d2d's `player_walk` gives near 1 to every unit (V read on both sides).
