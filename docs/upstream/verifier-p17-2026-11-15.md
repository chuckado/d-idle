## Required changes

0. **Unused include (high, CI).** Remove `#include <sequences.hpp>` from `tests/game/test_seq_rate.cpp` in the oracle commit (above).

1. **Dual wield (medium).** Frenzy and Double Swing need two weapons and Double Throw two throwing weapons, so in play they always reach FUN_00623f50's dual-wield step (`0x624211..0x62428e`: the percent gets the two hands' stat 68 averaged). The oracle hooks FUN_006235a0 to "no dual wield" and the grid wears one main-hand weapon only. The -30 itself is not affected: both paths join at `0x624290` before the `sub esi, 0x1e` (V read), so the rule holds with two weapons. But the body should say in Limits: "the grid is single-weapon; the term sits after game.exe's dual-wield average (0x624290), which this PR does not compare". Without that line a reviewer may read the 7,600 cells as covering Frenzy as played.
2. **README row overclaims the length (low).** `tools/emu/README.md` says "its rate ... and so its length `ceil(256 steps / rate)`". The compare feeds d2d's own steps and AnimData speed into the game side, so only the percent is compared. Write "its rate (the length counted as `ceil(256 steps / rate)` on both sides; the steps and the AnimData record are d2d's)".
3. **Test comment and body list (low).** `test_seq_rate.cpp` says "every skill whose anim is SQ", but game.exe has two more player SQ records the grid leaves out: Leap (132) and Dragon Flight (275), both the other branch (byte +6 = 0x06 and 0x42, no UseAttackRate bit; `seq_rate.py table`, V run). d2d's term is 0 for them (no UseAttackRate), so nothing changes; add them to the comment's "moving ones" or to the skill list, and to the body's "Charge, Leap Attack, ..." list.

4. **Body has no `## Checklist` (medium, process).** Every earlier body (`missile-block-body.md` and the others) has the three boxes the upstream template asks for; this one has none. Add before "Answers to the presubmit WARNs": test in `tests/` (`test_seq_rate`), finding in `docs/research/re/` (`combat.md`), `tools/pr_guard.py upstream/main` passes (0 FAIL, 0 WARN).

## Game side, re-derived (V read)

- FUN_00623f50 attack branch `0x6241d7..0x62430a`: FUN_00621580 picks it; FUN_00623c80(unit, 1) (return ignored); `ebx = FUN_00621740(unit, 0)` (effective IAS); `esi = ebx + stat 0x44` (68); dual wield `0x624211..0x62428e`; **`0x624290 cmp [edi], 0; jne; 0x624295 cmp [edi+0x10], 0x12; jne; 0x62429b sub esi, 0x1e`**; clamp 15..175 (`0x62429e..0x6242b2`); state 0x26 may swap the AnimData speed for FUN_00646170's; rate = speed x esi / 100, stored at `+0x3c` and `+0x4c`. This is the trace's reading, confirmed.
- FUN_006216e0 (called first, `0x623fc2`): player mode 0xa, or mode 0x12 with the active skill's record byte `+0x12` = 0xa (SC), takes the cast branch. So SC wins over UseAttackRate, as `sequence_sias` writes it.
- FUN_00621580: for a player the row is `0x6e8a00 + 20 x mode`; `+0xc` set returns 1 outright, else `+8` set and the record byte `+6` & `[0x6ce274]`. `table` prints the mask: 8 (V run).
- The other branch (`0x62430d`): FUN_00621630, else stat 0x45 (69) clamped 15..175. This is D3 of the trace.
- Call site `0x624429..0x62443f`: mode 0x12 runs FUN_00621260 (sequence init) and then FUN_00623f50, so the rate replaces the init value.
- `seq_rate.py table` (V run, the booted 1.14d image on the builder): 35 records in the attack branch at 179 (= 256 x 70 / 100), 2 cast at 256 (Lightning 49, Chain Lightning 53), 79 other at 332. Player records in the attack branch: Jab 10, Impale 19, Double Swing 133, Double Throw 140, Frenzy 147, Fists of Fire 259, Dragon Claw 260, Claws of Thunder 269, Blades of Ice 274; the rest are monster rows (156, 215, 281..331). ## Brief question 4: is the rate term alone enough for a PR?

Yes. The PR changes only the percent and proves exactly that over every attack-branch player record game.exe has.
