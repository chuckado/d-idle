## Verdict: PASS (one recommended harness line, not blocking)

1. The empty-path rule is fixed in `compare` and in the test (V read, V run). The 426 to 427 starts that are now "not compared" hide no plan mismatch: in every one, d2d's own unit plan for the same start (the dump's `D` line, the same `player_walk` with a unit target) equals game.exe's path, and the outcome matches the model in all of them (V run, table below).
2. **The nondeterminism has a source, and it is not in the PR's code or in the oracle.** d2d builds levels on `std::async` threads (`GameData::want_level`, `gamedata.cpp:1396`) and links a level to its neighbours (`Level::nearby`, `install_level`) only when a build is collected. `Level::blocked` past a map's edge asks `nearby`; when the neighbour is not linked yet, everything past the edge is blocked. Which neighbours are linked when a start runs depends on thread timing. With every level built and linked before the first start (a one-line verifier patch), three runs are byte-identical (V run). The PR's claim is per start (each start's own bits go to the oracle), so the variation changes which starts exist and what some edge bits are, not whether d2d's plan equals game.exe's on the same bits: still **0 differ** on every run.

## Item 2: the nondeterminism

**Bound (V run).** Five `--dump 30` runs of the same claim binary on the same data (one from p1, four concurrent repeats), keyed per start (seed, level, warp, direction) instead of a line diff (a line diff overcounts, the start lists shift):

| repeat vs run 1 (45,976 start keys) | starts with any line different | `G` (window bits) differ | `D` / `T` (plans) differ | `W` (outcome) differ |
|---|---|---|---|---|
| 2 | 1,121 | 1,121 | 35 / 35 | 34 |
| 3 | 841 | 841 | 29 / 29 | 28 |
| 4 | 670 | 670 | 26 / 26 | 25 |
| 5 | 807 | 807 | 27 / 27 | 26 |

So up to about 2.4 % of the starts see different bits somewhere in their 193 x 193 subtile window, and up to about 0.08 % (35) get a different plan or outcome. Every differing start is in Act 3 to 5 outdoor or linked levels (76, 80 to 82, 92, 93, 97, 100, 101, 112, 119, 122 to 124, 128). The author's "13 of about 46,000 lines" undercounts: most differences are in the `G` window lines, which hold no plan.

**Source (V run, V read).** `GameData::want_level` starts every level build with `std::async(std::launch::async, ...)` (`components/game/gamedata/gamedata.cpp:1396`); `poll_levels` / `level()` install a finished build and only then link it with the levels already there, both ways (`install_level`, `Level::nearby`). `Level::blocked` (`gamedata.hpp`, the `nearby` loop) answers a point past the map's edge from a linked neighbour, and from nothing (blocked) when the neighbour is not linked yet. Which neighbours are linked when a start is taken depends on how far the worker threads have got. Evidence:
- Smallest repro: the same binary, `--dump 2` over all levels, three concurrent runs: run 3 differs from run 1 in 251 lines starting at level 82 warp 2, whose window in run 3 is all `f` (everything blocked: the neighbour past the edge missing). Act 1 only (`--levels 1 40`), three serial runs: identical. Under ASan (slower threads) Act 1 also varies: levels 33 to 37 (the Cathedral and Catacombs, linked act levels), 107 lines.
- The test: a verifier-local line after the data loads, `for (int pre = 1; pre <= 136; ++pre) (void)data->level(pre);` (builds and links every level synchronously before the first start; local `3b1be0b3`): three concurrent `--dump 2` runs are **byte-identical**, and 4 more starts exist (1,411 vs 1,407: starts that were "blocked" only because the neighbour was missing).
- ASan + UBSan build of `test_warp_walk` (clang 19, `-fsanitize=address,undefined`, halt on error): the no-argument test (`OK: 8 of 8`) and two Act 1 sweeps run clean, 0 reports (V run). Uninitialised reads (MSan) were not checked (no instrumented libc++ on the builder; U), but the prebuild run being byte-identical leaves no room for another source in this harness.

**Does it touch the claim? No.**
- It is in d2d's level loader, not in `tick.cpp` (the PR's one line) and not in the oracle (`warp_walk_path.py` is single-threaded and reads only the dump).
- `compare` gives game.exe each start's own `G` bits, the bits d2d's walk saw (taken after the warm-up ticks, just before the click). A neighbour linked during the 600 ticks after that could change what d2d's walk meets later (outcome, not the first plan); that is part of the 25 to 34 outcome changes per repeat, on both builds.
- **Deterministic rerun (prebuild patch on the claim and on the mutant, `--dump 30`, V run):** 21,031 starts on both; claim **0 plan differ** (20,890 equal, 466 discriminating; 124 no path, 17 town), mutant **436 differ**, outcome 147. The claim's outcome differs in **2** starts, both level 40 (Lut Gholein) warp 2 direction 5 (seeds 1 and 28): d2d's plan equals game.exe's one-point path, game.exe reaches distance 0, d2d's walk does not take the warp in 600 ticks; the mutant has the same 2. A town crowd case (the first pass saw the same start with seed 7), not the plan and not the fix. So with the harness made deterministic, `compare` on the claim needs `--outcome-known 40:2` (or the town rule for outcomes too) to print OK.
- The no-argument test: 30 of 30 runs OK on the claim, 10 of 10 FAIL on the mutant, under a loaded builder (V run); its levels (2, 6, 17, 46, 52, 76, 113, 118) are not among the varying ones in my repeats. Not flaky in practice; with the prebuild line it cannot be.
