## FUN_0057edd0 read (V read, capstone over game.exe; jump tables decoded)

`FUN_0057edd0(unit = EAX, new mode = EBX, game = ECX)`:

1. `+0x60` branch (`0x57edd3..0x57edf4`): if `unit+0x60` is non-null and `FUN_0063c1e0(unit+0x60)` is non-zero and `new != 0`, the answer is "refused" unless `new == 0x11`. `FUN_0063c1e0` returns `obj+0x20` when `obj` carries the signature `0x1020304` (the inventory's), so the test is "the player holds an item on the cursor" (+0x20 = cursor item: S, the usual inventory layout). V run (my own harness, `ms20.py` in the reproduce dir): with an inventory whose +0x20 is non-zero, GH is refused from **every** mode 0..20; with +0x20 = 0 the answers equal the oracle's `+0x60 = 0` run. **This branch only refuses more; it can never make GH-from-GH allowed, so it cannot make the claim wrong.** (It is a separate, untouched d2d question: a player holding a cursor item never enters GH in game.exe.)
2. New-mode table (`0x57ee78`, targets `0x57ee70`): new 0, 1, 5, 17 are allowed at once; every other new mode up to 0x11 goes to the current-mode table; new > 0x11 (e.g. 0x13 KB) also goes there (`ja 0x57ee08`).
3. Current-mode table (`0x57eea8`, targets `0x57ee8c`), for new GH (4):
   - DT (0), GH (4), BL (9), DD (17): `0x57edf0`, **refused, unconditionally** (no event, class or game read).
   - A1 (7), A2 (8), SC (10), TH (11): `0x57ee1e`, allowed for new 4 and 9 whatever `FUN_0057ed70` says.
   - KK (12): `0x57ee38`, `FUN_0057ed70 != 0` (allowed only with a queued end event).
   - S1 (13): refused for class 0 only; S3 (15): refused for class 5 only (`cmp [esi+4], 5`).
   - mode 18: `FUN_0057ed90`.
   - anything above 0x12, **including 0x13 (KB)**: `cmp eax, 0x12; ja 0x57ee68`, **allowed**. V run: GH allowed from 19 and 20 with and without an end event.
4. Caller (`0x57d364..0x57d3c3`, V read): flag 2 goes to `FUN_00580a70` mode 0 and returns; flag 8 goes to `FUN_00580a70` mode **0x13** (the knockback) and returns; flag 4 (landed): state 0x15 goes straight to the get-hit call, else `FUN_0057cb00`; non-zero = too small: `FUN_0064c040` and `or [unit+0xc4], 0x8000` (the struck cue); zero: `FUN_005809d0(game, unit, 4, unit+0x4c, 0, 0)` and return. The three flags are an if-else chain: one hit is a knockback OR a get-hit, never both.
5. `FUN_005809d0` (`0x5809fd`): calls `FUN_0057edd0` first; on 0 it returns at once (`0x580a62`): no state, no flag, no event. When allowed, `FUN_0057eec0` can still refuse (state 0x36 among others): it only refuses more.

### What the 12 cells miss

The author's doc labels mode 18 "KB"; in PlrMode.txt order mode 18 is SQ (sequence) and KB is 0x13 = 19 (S for the table order; V read that d2d's own comments call the knockback "mode 0x13": `fight.hpp:267`, `tick.cpp:626`). The oracle loops `range(0, 19)`, so the mode d2d folds into `kModeGH` (KB, 0x13) is never asked, and the d2d probe never sets `actor->knock`. The class-dependent cells are two, not one: the Amazon in S1 and the **Druid in S3** (the author's doc names only the Amazon; both are swing modes, excluded, harmless).
